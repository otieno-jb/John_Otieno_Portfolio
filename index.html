LAB 01 WEB
Web exploitation · OWASP Top 10

Broken access control in a local e-commerce lab

Completed A01:2021

Problem statement

A deliberately vulnerable training shop exposed a basket API. The question: does the server verify that the authenticated user actually owns the basket it returns, or does it trust the object ID supplied by the client?

Tools used

Kali Linux Burp Suite CE Nmap OWASP Juice Shop Firefox DevTools

Environment

Isolated Docker lab · synthetic accounts · localhost only.

Approach

  1. 01

    Ran service discovery against the lab host and mapped the application entry points.

  2. 02

    Created two standard accounts and captured authenticated basket requests in Burp Suite.

  3. 03

    Replayed the request with a different basket ID and compared the response to the expected object.

  4. 04

    Confirmed horizontal privilege escalation, documented the request/response pair, then tested the proposed server-side ownership check.

Evidence sanitized capture

kali@lab — zsh 
$ curl -s -H "Authorization: Bearer <redacted>" \
    http://10.10.10.20:3000/rest/basket/2

HTTP/1.1 200 OK
{ "id": 2, "UserId": 2, "Products": [...] }

# basket 2 belongs to another user
$
Impact High — horizontal privilege escalation

Key lessons learned

  • Object IDs are not authorization. Every request needs a server-side ownership check, even when the ID is hard to guess.

  • Test with two identities. A single logged-in account can make an access-control flaw invisible.

  • Log the denied path. Repeated 403s and sequential object access are useful signals for detection and review.

Remediation & detection notes
Remediation

Enforce object-level authorization inside the API layer; bind basket IDs to the authenticated subject; return 404 for unauthorized objects to reduce enumeration signal. Add authorization tests for every route and use unguessable identifiers as defence in depth — never as the only control.

Detection idea

Alert on a single identity requesting a high volume of sequential basket IDs, and on repeated 403/404 responses from an authenticated session. Correlate with normal baseline behaviour per user.

LAB 02 SOC
SOC triage · Windows telemetry

RDP brute force: did the attacker get in?

Completed T1110.001

Problem statement

A Windows server generated 1,284 failed logons from one external address in under 20 minutes, followed by a single success. Determine whether the account was compromised, scope the activity and recommend containment.

Tools used

Splunk Free Windows Event Logs Sysmon PowerShell MITRE ATT&CK

Environment

Windows 11 VM + Splunk · synthetic logs · no live external host.

Approach

  1. 01

    Scoped the time window and grouped Event ID 4625 by account, source IP and logon type.

  2. 02

    Found the failure burst, then searched for a 4624 success from the same source immediately after it.

  3. 03

    Pivoted into Sysmon process creation for the successful session to identify discovery activity.

  4. 04

    Documented the timeline, contained the lab host, disabled the account and wrote a correlation search.

Evidence sanitized capture

splunk — search 
index=winlogs EventCode=4625
| stats count min(_time) as first max(_time) as last
  by IpAddress, TargetUserName, Logon_Type
| where count > 50

IpAddress        User          Count  Type
185.220.101.47   svc_backup    1284   10
+ 4624 success → 4672 special privileges
$
Verdict Compromise confirmed — isolate host

Key lessons learned

  • One success changes the story. A brute-force alert becomes an incident when a failed burst is followed by a successful logon.

  • Service accounts need baselines. Their normal logon patterns are different, and noisy alerts hide the real signal.

  • Preserve before you contain. Export the relevant events and note the timeline before isolating or reimaging.

Detection query & response notes
Correlation logic

Threshold more than 20 failures per account/IP in 10 minutes, then trigger a high-severity alert if a 4624 success from the same source follows within 15 minutes. Enrich with 4672 and Sysmon event 1 to show what ran next.

Containment

Isolate the host, disable the targeted account, reset credentials, block the source at the perimeter, and review remote-access exposure. Add MFA and restrict RDP to a managed access path.

LAB 03 FOR
Network forensics · PCAP analysis

Finding a DNS tunnel in 63% noise

Completed T1071.004

Problem statement

A workstation was making roughly 1,440 DNS queries per day to long, random-looking subdomains of the same domain. Determine whether this was normal telemetry or an active DNS tunnelling channel — and identify the affected host.

Tools used

Wireshark tshark CyberChef Zeek Suricata

Environment

Synthetic PCAP · isolated capture · domain reserved for the exercise.

Approach

  1. 01

    Reviewed protocol hierarchy and conversations to find the dominant talker and isolate DNS traffic.

  2. 02

    Filtered on the suspicious domain, measured query length and entropy, and checked for a regular beacon interval.

  3. 03

    Extracted subdomain labels with tshark, decoded the base32 payload in CyberChef and recovered the test marker.

  4. 04

    Mapped the infected host, wrote a Suricata rule and recommended DNS logging with response-policy zoning.

Evidence sanitized capture

tshark — lab.pcap 
$ tshark -r lab.pcap -Y 'dns.qry.name contains "telemetry-sync.example"' \
  -T fields -e frame.time -e ip.src -e dns.qry.name | head -3

03:14:02 10.10.20.14  aGVsbG8td29ybGQ....telemetry-sync.example
03:15:02 10.10.20.14  c2Vzc2lvbi03....telemetry-sync.example

$ base32 decode → {"session":"lab-07","host":"WS-014"}
$
Verdict Tunnelling confirmed on WS-014

Key lessons learned

  • DNS is often the permitted path. Attackers use it because it is almost always allowed outbound.

  • Anomalies are relative. Query length, entropy and periodicity only mean something against a baseline.

  • Find the host, not just the domain. Blocking the domain is containment; identifying the infected endpoint is the investigation.

Detection rule & next steps
Detection idea

Alert when a single host exceeds a learned baseline of unique subdomains for one parent domain, especially where labels are long, high-entropy and spaced at a regular interval. Retain DNS query logs and enrich with process attribution from Sysmon or Zeek.

Next steps

Isolate the endpoint, capture volatile evidence, review scheduled tasks and autoruns, and check for data staging. Hunt for the same domain pattern across the estate before blocking.
